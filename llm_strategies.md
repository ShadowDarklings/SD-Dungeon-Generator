# LLM Strategies — Attack-Path Test Approaches (Mario)

This document contains the conversation about alternative test strategies for the attack-path problem, followed by my assessment.

## Part 1: The Prompt

"Our project uses a parametrized pytest (`test_attack_paths.py`) with a JSON fixture of 20 known-bad paths (WordPress admin, dotfiles, admin panels, server diagnostics). Each path is tested with `requests.get(https://localhost + path)` and asserts a 404 or 403. What other strategies exist for the same problem — catching malicious or scanner traffic before it reaches our Flask app? For each strategy, give me an honest read on what it catches that our approach doesn't, and what it misses."

## Part 2: LLM Response

### Strategy 1: Automated vulnerability scanners (Nikto, OWASP ZAP, Nessus)

These tools maintain databases of thousands of known-bad paths, headers, and payloads. They actively crawl your application, testing not just paths but also parameter injection, header manipulation, and cookie tampering.

**What it catches that yours doesn't:**
- Paths not in your 20-item list — Nikto's database has ~7,000 entries including server-specific paths (`/server-info`, `/jmx-console/`, `/solr/admin/`), backup file patterns (`/index.html.bak`, `/app.py.swp`), and version-specific exploit paths.
- Response-based detection — a scanner can identify that a 200 response on `/server-status` is leaking connection info even if the path isn't in your list.
- Header analysis — scanners check if `X-Powered-By`, `Server`, or debug headers leak stack information.

**What it misses:**
- Application-specific logic. A scanner doesn't know that `GET /api/runs/999` returning 200 is a BOLA vulnerability specific to your app — it just sees a valid HTTP response.
- It's slow (minutes for a full scan) and noisy (hundreds of findings, many false positives). Not suitable as a CI gate that must pass on every PR.
- Non-deterministic — network timing, server state, and scan ordering can produce different results on different runs.

### Strategy 2: Web Application Firewall (WAF) rules

Instead of testing paths, deploy a WAF (ModSecurity with OWASP Core Rule Set, or a cloud WAF like AWS WAF) that blocks malicious patterns in real-time based on regex rules applied to the request URI, headers, and body.

**What it catches that yours doesn't:**
- Dynamic patterns: a WAF can block any request containing `../` (path traversal), `' OR 1=1` (SQL injection), or `<script>` (XSS) regardless of the specific path.
- Zero-day scanner paths — when a new WordPress exploit drops, the WAF rule set gets updated before your JSON fixture does.
- Rate-based rules — block an IP that sends 100 requests to different paths in 10 seconds (scanner behavior).

**What it misses:**
- Legitimate requests that match a pattern. A WAF blocking `../` would break a valid URL that contains those characters. Tuning false positives is a full-time job.
- Business logic vulnerabilities — a WAF doesn't know that your `/api/runs` endpoint has an ownership check that should return 404 for non-owners.
- It's an operational dependency, not a test. You can't run it in CI to verify your config is correct — you'd need a separate test that the WAF blocks what you expect.

### Strategy 3: Behavioral/semantic tests

Instead of listing specific paths, test *properties* of your system: "any request to a path that doesn't match a registered Flask route should return 404 with no information leakage in the body."

**What it catches that yours doesn't:**
- The entire class of unknown paths, not just the 20 you listed. If someone adds a new route that accidentally exposes internal state, a behavioral test catches it.
- Information leakage in error pages — you can assert that 404 responses don't contain stack traces, file paths, or server version strings.

**What it misses:**
- Hard to define "registered route" without duplicating your URL map. You'd need to enumerate valid routes, which is fragile if routes change.
- Doesn't test that nginx specifically is blocking the request (vs. Flask returning 404) — the behavioral distinction matters because nginx blocking is cheaper and doesn't occupy a worker.
- More complex to write and maintain than a simple fixture list.

### Strategy 4: Fuzz testing (e.g., ffuf, wfuzz, Burp Intruder)

Feed a wordlist of tens of thousands of paths to a fuzzer and observe which ones return non-404 responses. The approach is discovery-oriented: you're looking for paths you didn't know existed.

**What it catches that yours doesn't:**
- Undocumented routes — if Flask has a route you forgot about (like the `/test/login/<username>` backdoor that should be guarded by `TESTING`), a fuzzer would find it returning 200 or 302.
- Paths generated by framework defaults — Flask's built-in debugger at `/__debugger__`, or Werkzeug's `/console` endpoint if debug mode leaks into production.

**What it misses:**
- Authenticated surfaces — a fuzzer without a session cookie can't test what happens behind `@login_required`.
- Very slow for CI — a wordlist with 50,000 entries takes minutes even against a local server.
- High noise — most paths return 404, and the interesting ones (302 redirect to login) require manual interpretation.

### Strategy 5: Infrastructure-as-code static analysis

Lint your `nginx.conf` and `docker-compose.yml` for known misconfigurations without running the stack. Tools like `gixy` (nginx config analyzer) or `hadolint` (Dockerfile linter) catch issues statically.

**What it catches that yours doesn't:**
- Config errors that don't manifest as a wrong HTTP status code. For example, `gixy` can detect that your `alias` directive with a `location` that doesn't end in `/` is vulnerable to path traversal — even if your test doesn't hit the right path to trigger it.
- Dockerfile issues like running as root, missing `USER` directive, or `COPY .env .` accidentally included.

**What it misses:**
- Runtime behavior — a static analyzer can't tell you whether nginx is actually serving the right content, only that the config syntax is correct.
- Application logic entirely — it knows nothing about Flask routes, SQLModel, or your authorization rules.

## Part 3: My Assessment

### Why the parametrized approach is what it is

Our `test_attack_paths.py` is the right choice for our scope because:

1. **It's deterministic.** Same input, same output, every time. It runs in 2 seconds against a live stack and can gate a CI pipeline without flakiness.
2. **It documents the threat model.** The 20 paths in `attack_paths.json` are a readable, reviewable list of exactly what we're defending against. A new team member can read the JSON and understand the security posture.
3. **It tests the actual deployed behavior.** Unlike a static analyzer, it confirms that requests to these paths actually return 404/403 through the full nginx→gunicorn→Flask chain.

### What it doesn't catch

- Paths not in the list (e.g., `/.docker/config.json`, `/debug/vars`, `/graphql`)
- Non-GET attacks (verb tampering, large payloads)
- Response content (a 404 that leaks a stack trace is still a 404)
- Header-based information leakage
- Application-layer authorization bugs

### What I'd add if security were higher stakes

1. **A nightly OWASP ZAP scan** as a non-blocking CI job that posts findings to a Slack channel. It catches the breadth we miss, and running nightly avoids the CI gate slowdown.
2. **Behavioral assertions** on error response content: every 404 response body should be identical regardless of the path requested (prevents path-based fingerprinting).
3. **A header leakage test**: assert that responses don't contain `X-Powered-By`, and that `Server` doesn't reveal the exact nginx version. This is a one-time addition to our existing test.
4. **`gixy` in CI** to lint `nginx.conf` statically. It runs in milliseconds and catches alias/root misconfigurations before they reach production.
5. **A path traversal test** specifically for our `alias` directives: `GET /site/../app.py` and `GET /static/../requirements.txt` should both return 404, not the file contents.
